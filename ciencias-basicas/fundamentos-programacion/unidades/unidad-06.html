Desarrollo 1

Calidad como conjunto de propiedades verificables

Un programa que produce el resultado esperado en un ejemplo no está necesariamente bien construido. La calidad incluye corrección, robustez ante entradas inesperadas, claridad, eficiencia suficiente, facilidad de prueba, mantenibilidad y trazabilidad. Estas propiedades pueden entrar en tensión: optimizar prematuramente puede reducir legibilidad; añadir flexibilidad sin necesidad puede aumentar superficie de error; una interfaz muy breve puede ocultar unidades o supuestos.

La especificación define qué debe hacer el programa y bajo qué condiciones. Sin una especificación, una prueba puede confirmar solo que el código repite su comportamiento actual. En software científico deben declararse fórmulas, unidades, rangos, tratamiento de faltantes, precisión numérica y significado de la salida. Los criterios de aceptación convierten requisitos generales en observaciones comprobables.

La revisión de código busca defectos y mejora comprensión compartida. Debe examinar nombres, contratos, duplicación, dependencias, complejidad, errores y pruebas, no limitarse al estilo. Herramientas de formato, linting y análisis de tipos automatizan comprobaciones repetitivas, pero no determinan si el algoritmo responde a la pregunta científica correcta.

Los requisitos deben conectarse con pruebas mediante trazabilidad. Si el requisito dice que ninguna fila inválida se descarta sin registro, una prueba de integración debe comprobar los conteos y mensajes. Una prueba que replica la implementación línea por línea aporta poca independencia. Las pruebas basadas en propiedades, como verificar que una conversión seguida de su inversa recupera el valor dentro de tolerancia, examinan familias de casos y complementan ejemplos concretos.

Puntos de integración

  • La calidad no se reduce a que el código se ejecute.
  • Una especificación conecta requisitos con pruebas.
  • Las decisiones científicas deben aparecer en contratos y documentación.
  • Las herramientas automáticas complementan, no sustituyen, la revisión conceptual.

Desarrollo 2

Pruebas, errores y observabilidad

Una prueba unitaria comprueba una función o componente aislado. Una prueba de integración evalúa la interacción entre componentes, por ejemplo lectura, validación y cálculo. Una prueba de regresión conserva un caso que falló anteriormente para impedir que el defecto reaparezca. El conjunto debe cubrir casos normales, fronteras, entradas inválidas y propiedades generales, no solo ejemplos favorables.

Los números de punto flotante rara vez deben compararse con igualdad exacta después de operaciones. Las pruebas usan tolerancias absolutas o relativas justificadas. Una tolerancia demasiado estricta puede fallar por representación numérica; una demasiado amplia puede aceptar errores relevantes. El valor debe relacionarse con precisión del método y necesidad del problema, no elegirse solo para hacer pasar la prueba.

Las excepciones informan que una operación no puede cumplir su contrato. Deben ser específicas y conservar contexto. Capturar Exception sin volver a lanzar ni registrar puede ocultar corrupción de datos. El logging permite registrar eventos con niveles y metadatos, pero no debe exponer información sensible. Los mensajes útiles indican operación, entrada relevante no sensible y acción recomendada.

La depuración es un proceso de formulación y contraste de hipótesis. Primero se reproduce el fallo con la entrada mínima, se observa el traceback, se inspecciona el estado y se localiza la primera desviación respecto al contrato. Añadir prints indiscriminadamente puede alterar el comportamiento y generar ruido; un depurador, logging estructurado o aserciones temporales permiten observar con propósito. Después de corregir, el caso se conserva como prueba de regresión.

Puntos de integración

  • Las pruebas cubren comportamiento normal, fronteras, errores y regresiones.
  • Las comparaciones numéricas requieren tolerancias justificadas.
  • Las excepciones específicas hacen visibles los incumplimientos del contrato.
  • El logging aporta trazabilidad sin reemplazar el manejo de errores.

Desarrollo 3

Reproducibilidad, versiones y ciclo de cambio

Un entorno reproducible registra versión de Python y dependencias. Los entornos virtuales aíslan paquetes entre proyectos. Un archivo de requisitos o configuración fija rangos o versiones según el nivel de control necesario. Guardar únicamente el código no basta si una actualización de biblioteca modifica resultados o elimina una función. También deben registrarse datos de prueba, semillas aleatorias y parámetros.

El control de versiones almacena cambios como commits con propósito definido. Una rama permite desarrollar sin alterar la versión estable; un pull request facilita revisión y ejecución automática de pruebas. Los commits deben ser pequeños, coherentes y describir por qué se hizo el cambio. Los datos sensibles, secretos y archivos generados grandes no deben incluirse sin una política explícita.

La integración continua ejecuta validaciones ante cambios y reduce errores repetitivos. No certifica por sí sola seguridad o eficacia. En contextos clínicos, el ciclo incluye gestión de riesgos, requisitos, verificación, validación, trazabilidad y control de cambios bajo normas aplicables. El código educativo o de investigación debe etiquetarse según su finalidad para evitar que se use fuera de alcance.

La reproducibilidad incluye configuración y datos, no solo dependencias. Los parámetros no deberían quedar dispersos como números mágicos; pueden centralizarse en argumentos o archivos de configuración versionados. Las semillas controlan parte de la aleatoriedad, pero no garantizan resultados idénticos entre bibliotecas, hardware o paralelismo. El informe debe distinguir repetibilidad en el mismo entorno, reproducibilidad en otro entorno y validez del resultado científico.

Puntos de integración

  • La reproducibilidad requiere código, entorno, datos, parámetros y semillas.
  • El control de versiones documenta la evolución y facilita revisión.
  • La integración continua automatiza comprobaciones consistentes.
  • El uso clínico exige procesos de ingeniería y regulación adicionales.

Desarrollo 4

4. Del prototipo al proyecto mantenible

Un proyecto mantenible tiene una estructura predecible: código fuente, pruebas, documentación, configuración y datos de ejemplo separados. El README explica instalación, ejecución, entradas, salidas y límites. Un archivo pyproject.toml puede centralizar metadatos y herramientas. La estructura debe ser proporcional al tamaño; el objetivo es hacer visibles las responsabilidades, no imitar una empresa con carpetas vacías.

Los commits registran unidades de razonamiento. Un buen commit modifica un propósito, incluye pruebas relevantes y deja el proyecto ejecutable. Una rama facilita experimentar y un pull request reúne explicación, diff y evidencia automática. Reescribir el historial compartido o mezclar refactorización con cambios científicos dificulta revisar qué alteró el resultado.

La integración continua ejecuta formato, linting, análisis de tipos, pruebas y validaciones de artefactos. Cada control tiene alcance: un linter encuentra patrones, mypy evalúa anotaciones bajo supuestos y pytest ejecuta casos. Pasar todos no demuestra que la pregunta sea correcta ni que el software sea seguro. El pipeline debe fallar de forma comprensible y producir registros suficientes para investigar.

La entrega final incluye una declaración de finalidad. Un prototipo educativo puede explorar datos sintéticos; una herramienta de investigación necesita validación metodológica y gestión de datos; software destinado a decisiones clínicas entra en procesos de calidad, riesgo y regulación. Etiquetar versión, uso previsto y limitaciones reduce la posibilidad de que un resultado se reutilice fuera de alcance.

Puntos de integración

  • La estructura del proyecto hace visibles código, pruebas, datos y configuración.
  • Los commits y PR deben facilitar revisión causal de los cambios.
  • CI automatiza evidencia parcial, no certifica validez total.
  • La finalidad declarada delimita qué usos están respaldados.

Ejemplos y casos resueltos

Pruebas de una conversión de temperatura

Situación. Una función convierte Celsius a kelvin para un flujo científico. El contrato exige números reales y rechaza temperaturas inferiores al cero absoluto dentro de una tolerancia definida.

Razonamiento paso a paso

  1. El contrato define dominio, unidad y tipo de retorno.
  2. La prueba normal comprueba un valor conocido.
  3. La prueba frontera evalúa el límite físico permitido.
  4. La prueba inválida exige una excepción específica.
  5. La comparación usa una tolerancia pequeña en lugar de igualdad exacta arbitraria.

Limitaciones

  • La conversión matemática no valida un sensor de temperatura.
  • La tolerancia elegida corresponde al cálculo, no a precisión instrumental.
  • Un proyecto real usaría un framework de pruebas y más casos parametrizados.

Pruebas unitarias e integración para un importador

Situación. Se prueba una función pura de conversión y después el flujo que lee un archivo temporal, valida filas y devuelve datos y errores.

Razonamiento paso a paso

  1. El contrato define el comportamiento para denominador cero.
  2. El caso conocido se calcula manualmente.
  3. math.isclose expresa una comparación numérica aproximada.
  4. La prueba inválida exige la excepción específica.
  5. Una prueba de integración añadirá el archivo y los conteos de filas.

Limitaciones

  • Faltan pruebas de tipos, infinitos y NaN.
  • El ejemplo no mide cobertura ni propiedades.
  • Pruebas superadas no equivalen a validación clínica.

Actividad aplicada

Convertir un script en proyecto verificable

Procedimiento

  1. Selecciona un script previo con lectura, cálculo y salida.
  2. Escribe requisitos y contratos para sus funciones principales.
  3. Separa lógica pura de archivos, gráficos y presentación.
  4. Añade pruebas normales, frontera, inválidas y de regresión.
  5. Crea un entorno virtual y registra dependencias.
  6. Prepara commits pequeños y una revisión del cambio.

Problemas y tareas

  • Distingue prueba unitaria, integración y regresión.
  • Selecciona tolerancia para una conversión exacta en float.
  • Propón estructura mínima de proyecto.
  • Divide un cambio en commits revisables.
  • Traza requisito→función→prueba para no sobrescribir datos.
  • Explica qué no demuestra CI verde.

Criterios de comprobación

  • Los requisitos pueden comprobarse mediante pruebas concretas.
  • Las excepciones son específicas y no se silencian.
  • Las pruebas cubren límites y comportamiento inválido.
  • El entorno y las dependencias están documentados.
  • Los commits separan cambios conceptualmente distintos.
  • No se incluyen secretos ni datos identificables.

Errores frecuentes y autoevaluación

Errores frecuentes y corrección

  • Probar únicamente ejemplos que ya funcionan.

    Incluir fronteras, errores, regresiones y propiedades relevantes.

  • Capturar todas las excepciones y continuar.

    Capturar solo errores esperados, registrar contexto y propagar los no resueltos.

  • Comparar flotantes siempre con igualdad exacta.

    Usar tolerancias justificadas por el cálculo y la precisión requerida.

  • Guardar contraseñas o datos sensibles en el repositorio.

    Usar gestión de secretos y datos de prueba anonimizados o sintéticos.

  • No registrar versiones de dependencias.

    Documentar el entorno y automatizar su reconstrucción.

  • Confundir pruebas superadas con validación clínica.

    Limitar la afirmación a los requisitos y escenarios realmente evaluados.

  • Mezclar refactorización y cambio de fórmula en un commit.

    Separar cambios para que la revisión identifique qué alteró el resultado.

1. ¿Por qué ejecutar sin errores no demuestra calidad?

Respuesta: Porque faltan propiedades como corrección amplia, robustez, mantenibilidad, trazabilidad y reproducibilidad.

2. ¿Qué diferencia existe entre prueba unitaria e integración?

Respuesta: La unitaria comprueba un componente aislado; la de integración evalúa componentes conectados.

3. ¿Qué función cumple una prueba de regresión?

Respuesta: Evitar que reaparezca un defecto previamente identificado y corregido.

4. ¿Por qué se usan tolerancias numéricas?

Respuesta: Porque el punto flotante y los métodos aproximados pueden no producir igualdad exacta.

5. ¿Qué debe contener un mensaje de error útil?

Respuesta: La operación, la causa, contexto no sensible y una indicación que permita corregir el problema.

6. ¿Para qué sirve un entorno virtual?

Respuesta: Para aislar dependencias y reducir interferencias entre proyectos.

7. ¿Qué no demuestra una integración continua exitosa?

Respuesta: No demuestra por sí sola seguridad, eficacia clínica ni cumplimiento de todos los requisitos.

8. ¿Qué diferencia existe entre repetibilidad y reproducibilidad?

Respuesta: Repetibilidad busca el mismo resultado en condiciones cercanas; reproducibilidad evalúa reconstrucción en otro entorno o por otra persona.

9. ¿Qué es una prueba basada en propiedades?

Respuesta: Una prueba que verifica una propiedad general sobre múltiples entradas, no un único ejemplo.

10. ¿Por qué un commit debe tener un propósito coherente?

Respuesta: Porque facilita revisar qué cambio causó una modificación del comportamiento.

Glosario disciplinar

  • Especificación

    Descripción verificable del comportamiento y restricciones esperados.

  • Criterio de aceptación

    Condición observable usada para decidir si un requisito se cumple.

  • Prueba unitaria

    Prueba de una unidad pequeña de comportamiento aislado.

  • Prueba de integración

    Prueba de la interacción entre componentes.

  • Prueba de regresión

    Prueba que evita la reaparición de un defecto conocido.

  • Tolerancia numérica

    Margen permitido al comparar resultados aproximados.

  • Excepción

    Objeto que representa una condición que impide completar una operación.

  • Logging

    Registro estructurado de eventos durante la ejecución.

  • Entorno virtual

    Instalación aislada de intérprete y dependencias para un proyecto.

  • Commit

    Instantánea identificada de cambios en un sistema de control de versiones.

  • Integración continua

    Ejecución automatizada de pruebas y comprobaciones ante cambios.

  • Trazabilidad

    Relación documentada entre requisitos, código, pruebas, resultados y cambios.
