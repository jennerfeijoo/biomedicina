Unidad 2 de 6

Modelos de información

Modelar información clínica sin pérdida accidental de significado mediante una separación explícita entre modelo de referencia y contenido clínico, definiendo entidades, elementos, tipos de dato, cardinalidades, contexto, identificadores, referencias, versiones, procedencia y restricciones. La unidad reutiliza la semántica longitudinal de U1 y prepara la codificación terminológica de U3 y la interoperabilidad de U4, sin confundir una estructura válida con equivalencia semántica, conformidad de intercambio o utilidad clínica.

Objetivos y resultados esperados

  • Distinguir modelo conceptual, modelo lógico, modelo de referencia, instancia de datos y serialización, explicando qué significado se conserva o se pierde en cada capa.
  • Definir elementos clínicos mediante ruta, tipo de dato, cardinalidad, obligatoriedad, repetición, nulabilidad o ausencia y restricciones, evitando que un campo con el mismo nombre se trate automáticamente como el mismo concepto.
  • Representar contexto clínico, sujeto, encuentro, autoría y temporalidad como información explícita en lugar de depender de columnas implícitas o del orden físico de una tabla.
  • Distinguir identificadores de negocio, identificadores técnicos y referencias entre entidades, documentando sistema emisor, ámbito, vigencia y reglas de resolución antes de enlazar registros.
  • Conservar versiones, auditoría y procedencia al transformar información, diferenciando identidad de la entidad, identidad de una versión y actividad que produjo el cambio.
  • Aplicar restricciones, arquetipos o perfiles conceptuales a un conjunto sintético y demostrar mediante casos válidos e inválidos qué controla la estructura y qué sigue requiriendo terminología, interoperabilidad, gobernanza o validación posterior.

Desarrollo teórico

Los conceptos se estudian mediante mecanismos, modelos, evidencia, supuestos y límites de interpretación.

Desarrollo 1

1. Capas del modelo: concepto, referencia, instancia y serialización

Un modelo de información especifica cómo se representan entidades, atributos, relaciones y restricciones para que datos producidos en momentos y sistemas distintos puedan interpretarse de manera consistente. No es la base de datos concreta ni el archivo JSON que circula por una API. La misma idea clínica puede persistirse en tablas relacionales, documentos o grafos; por eso conviene separar la semántica del modelo de su representación física.

El modelo conceptual responde qué entidades existen y cómo se relacionan. El modelo lógico añade estructura computable: elementos, tipos, cardinalidades y referencias. El modelo físico decide tablas, claves, índices o formatos concretos. Saltar directamente desde una necesidad clínica a columnas de una base de datos mezcla decisiones de significado con decisiones de implementación y dificulta detectar pérdidas durante una migración.

Un modelo de referencia define un conjunto relativamente estable de clases y reglas generales que permiten construir instancias coherentes. ISO 13606-1:2019 publica un modelo de referencia para comunicar partes o la totalidad de una HCE; openEHR separa igualmente un Reference Model de definiciones clínicas de nivel superior. U2 usa esos enfoques para enseñar arquitectura de información, no para declarar que un estándar sea universalmente superior a otro.

La instancia es un conjunto concreto de datos que satisface —o viola— las reglas del modelo. Dos instancias pueden tener la misma estructura y significado clínico diferente; a la inversa, dos estructuras distintas pueden pretender representar el mismo fenómeno. Validar una instancia contra un esquema solo demuestra cumplimiento de ciertas reglas formales, no equivalencia semántica ni corrección clínica.

La serialización es una codificación externa de la instancia, por ejemplo JSON o XML. Cambiar de serialización no debería modificar el significado del modelo, pero puede introducir pérdidas si la transformación no conserva tipos, cardinalidades, identificadores, unidades o contexto. U4 tratará el transporte e intercambio; U2 se concentra en definir qué debe permanecer invariante antes de mover la información.

El enfoque de dos niveles de openEHR ofrece un ejemplo pedagógico útil: un modelo de referencia estable contiene estructuras generales y los arquetipos o plantillas restringen esas estructuras para conceptos clínicos concretos. ISO 13606-2:2019 también define un Archetype Model para representar arquetipos intercambiables. La lección no es memorizar nombres de clases, sino comprender que estructura estable y restricciones de dominio pueden evolucionar a ritmos diferentes.

Puntos de integración

  • Modelo conceptual, lógico y físico resuelven preguntas diferentes y no deben colapsarse en una sola capa.
  • Un modelo de referencia define estructuras generales; una instancia contiene datos concretos sujetos a esas reglas.
  • Una serialización expresa una instancia, pero no constituye por sí sola el modelo de información.
  • Validar estructura no demuestra equivalencia semántica ni corrección clínica del contenido.
  • La transformación entre representaciones debe preservar tipos, relaciones, contexto, identificadores y restricciones relevantes.
  • Modelos de dos niveles permiten separar estructuras estables de restricciones clínicas que evolucionan con mayor frecuencia.

Desarrollo 2

2. Elementos, tipos, cardinalidad y ausencia: hacer explícita la estructura

Un elemento de información necesita más que un nombre. Debe tener una definición, una ubicación dentro de una estructura, un tipo de dato, una cardinalidad y reglas de uso. FHIR ElementDefinition, por ejemplo, formaliza ruta, cardinalidad, tipo, definiciones, valores fijos o patrones y otras restricciones. Es un buen recordatorio de que «campo» no es sinónimo de «string opcional».

El tipo de dato restringe qué operaciones y significados son admisibles. Fecha, instante, cantidad, texto, booleano, identificador y referencia no son intercambiables aunque puedan serializarse como caracteres. Guardar todo como texto puede facilitar una importación inicial, pero traslada la ambigüedad al consumidor y hace más difícil comprobar unidades, orden temporal o integridad referencial.

La cardinalidad expresa cuántas ocurrencias están permitidas. Un elemento 0..1 puede faltar o aparecer una vez; 1..1 exige una ocurrencia; 0..* permite repetición. Obligatoriedad y repetición son dimensiones distintas. Convertir una colección de múltiples observaciones en una única celda separada por comas destruye estructura y puede perder el vínculo entre cada valor y su contexto.

Ausencia tampoco es un valor clínico ordinario. Debe distinguirse un elemento opcional no presente de una negación explícita, un valor desconocido, un dato no aplicable o un dato que existe en otro sistema. U1 ya separó dato faltante de ausencia documentada; U2 exige que el modelo pueda expresar esa diferencia sin recurrir a convenciones frágiles como cadenas vacías o números centinela.

Las unidades y cantidades muestran por qué tipo y contexto cooperan. El número 5 no informa si se trata de 5 mg, 5 mmol/L o cinco eventos. Un modelo robusto no separa arbitrariamente el valor de la unidad si esa asociación es parte de la semántica. U3 estudiará los códigos y sistemas terminológicos; U2 solo exige que la estructura permita conservar el concepto, el valor y sus calificadores sin mezclarlos.

Las restricciones pueden reducir el conjunto de instancias permitidas: fijar cardinalidades, exigir un contexto, limitar tipos o declarar invariantes. Un esquema inválido es un control negativo útil, pero un esquema válido sigue pudiendo contener un identificador equivocado, una unidad incorrecta o un concepto mal codificado. La validación estructural es necesaria en muchos flujos, pero no suficiente para garantizar significado.

Puntos de integración

  • Cada elemento necesita definición, ruta, tipo, cardinalidad y reglas de uso, no solo un nombre de columna.
  • Tipos de dato preservan operaciones y significado que se pierden cuando todo se convierte en texto.
  • Obligatoriedad y repetición son dimensiones distintas expresadas mediante cardinalidades explícitas.
  • Dato ausente, negación explícita, desconocido y no aplicable no deben codificarse como si fueran equivalentes.
  • Cantidad, unidad y calificadores deben permanecer asociados cuando su relación forma parte del significado clínico.
  • Una instancia estructuralmente válida todavía puede ser semántica o clínicamente incorrecta.

Desarrollo 3

3. Contexto y relaciones: evitar que el significado dependa de una columna implícita

El mismo valor puede significar cosas distintas según sujeto, encuentro, tiempo, método, autor o foco clínico. El contexto no es decoración alrededor del dato: participa en su interpretación. Un resultado sin sujeto verificable, sin tiempo clínicamente relevante o sin relación con el evento que lo originó puede ser inutilizable aunque el valor y el tipo sean formalmente válidos.

Las estructuras jerárquicas permiten mantener proximidad entre contenido y contexto, mientras las referencias explícitas permiten relacionar entidades independientes. Ninguna estrategia elimina la necesidad de definir alcance. Embebido y referenciado son decisiones diferentes: copiar el nombre del profesional dentro de cada resultado no equivale a referenciar una entidad de profesional cuya identidad y organización puedan resolverse de forma consistente.

Una relación necesita dirección y semántica. «A refiere a B», «A deriva de B», «A pertenece al encuentro B» y «A reemplaza una versión de B» no significan lo mismo. Un modelo que guarda solo dos identificadores conectados por una clave genérica puede preservar conectividad pero perder el tipo de relación que justificaba el enlace.

El contexto temporal también requiere granularidad. U1 distinguió tiempo clínico, autoría, emisión y registro. U2 debe asignar cada tiempo al elemento o entidad apropiada, en vez de añadir una sola columna timestamp a toda la tabla. Esa decisión afecta consultas retrospectivas, reconstrucción de versiones y análisis de latencia documental.

FHIR StructureDefinition y ElementDefinition ilustran cómo el significado de un elemento depende de una ruta y un contexto de definición. openEHR organiza contenido mediante clases como Composition, Section, Entry y estructuras de datos. Estos ejemplos muestran que la posición dentro del modelo aporta semántica; no se debe asumir que dos propiedades llamadas status o code son intercambiables fuera de su contexto.

En U2 se modela un pequeño episodio sintético de U1 como grafo lógico: sujeto, encuentros, problemas, solicitudes y resultados permanecen como entidades diferenciadas, con referencias tipadas y contexto. El objetivo no es construir todavía mensajes HL7 ni recursos intercambiables por API; U4 evaluará cómo transportar ese modelo entre sistemas.

Puntos de integración

  • Sujeto, encuentro, tiempo, autor y método pueden formar parte del significado de un dato clínico.
  • Embebido y referenciado son estrategias distintas y deben elegirse con reglas explícitas de identidad y actualización.
  • Una relación necesita tipo, dirección y condiciones; conectividad por sí sola no preserva semántica.
  • Cada marca temporal debe asociarse al evento que realmente representa.
  • La ruta y el contexto de definición participan en el significado de un elemento dentro del modelo.
  • U2 modela relaciones internas; U4 abordará su transporte entre sistemas y APIs.

Desarrollo 4

4. Identidad, referencias, versiones y procedencia

Un identificador de negocio identifica una entidad dentro de un sistema o ámbito emisor: número de historia, identificador de laboratorio o identificador nacional son ejemplos posibles. FHIR Identifier separa system y value y permite registrar periodo y asignador; la idea general es que el valor aislado rara vez es suficiente para garantizar unicidad fuera de su ámbito.

Un identificador técnico de una representación no necesariamente es el identificador de negocio del objeto real. FHIR distingue el identificador lógico de un recurso de los business identifiers, y sus Reference pueden contener una referencia resoluble o un Identifier cuando la representación concreta no es conocida. Confundir ambas capas produce enlaces frágiles durante migraciones, replicación o integración de fuentes.

Una referencia debe declarar qué entidad pretende señalar y qué regla permite resolverla. El enlace puede ser directo, lógico o mediado por un identificador, pero no se debe asumir que una cadena coincidente en dos sistemas representa la misma entidad. La resolución de identidad necesita ámbito, autoridad emisora y, cuando corresponda, procesos explícitos de reconciliación.

La identidad persiste mientras las versiones cambian. FHIR Resource.meta.versionId ejemplifica un identificador de versión que cambia cuando cambia el contenido del recurso. openEHR lleva esta separación más lejos mediante VERSIONED_OBJECT y VERSION, conservando estados previos y auditoría de los commits. El patrón común es distinguir «qué entidad es» de «qué estado de esa entidad estoy observando».

Procedencia describe agentes, entidades y actividades implicadas en la creación o transformación de información. No es equivalente a historial de versiones: una versión dice que existe un estado distinto; la procedencia ayuda a explicar quién o qué proceso lo produjo y en qué actividad. U1 introdujo la reconstrucción temporal; U2 incorpora esas relaciones como parte del modelo.

Una transformación auditable debe conservar un mapa origen→destino. Si un campo se deriva de varios elementos, si una unidad se convierte o si dos registros se consolidan, debe existir evidencia para reconstruir esa operación. U5 tratará acceso, consentimiento y auditoría organizativa; aquí la procedencia se estudia como propiedad informacional y técnica.

Puntos de integración

  • Un identificador necesita ámbito o sistema emisor; el valor aislado puede no ser globalmente único.
  • Identificador de negocio e identificador técnico de una representación cumplen funciones distintas.
  • Una referencia requiere reglas de resolución y no convierte automáticamente coincidencia de cadenas en identidad.
  • Identidad de la entidad e identidad de una versión deben permanecer separadas.
  • Procedencia complementa el versionado al documentar agentes, actividades y transformaciones que produjeron un estado.
  • Las transformaciones deben conservar un mapa auditable entre datos de origen y representación resultante.

Desarrollo 5

5. Restricciones, arquetipos y contratos de datos: controlar sin confundir conformidad con significado

Un modelo de referencia deliberadamente general admite muchas instancias. Para un uso concreto se necesitan restricciones adicionales: qué elementos son obligatorios, qué repeticiones se permiten, qué tipos se aceptan y qué invariantes deben cumplirse. FHIR StructureDefinition utiliza ElementDefinition para definir estructuras, extensiones y restricciones; U2 lo toma como ejemplo de contrato estructural, no como entrenamiento de perfiles interoperables de U4.

El enfoque de arquetipos formaliza restricciones de dominio separadas del modelo de referencia. ISO 13606-2:2019 define un Archetype Model para comunicar arquetipos entre repositorios y servicios. openEHR adopta un enfoque de dos niveles en el que arquetipos y plantillas restringen un Reference Model estable. Esto permite que conceptos clínicos evolucionen sin rediseñar continuamente las clases básicas del sistema.

Una plantilla puede combinar o restringir arquetipos para un contexto de uso más específico. Sin embargo, mayor restricción no siempre significa mayor interoperabilidad. Dos organizaciones pueden usar estructuras formalmente válidas pero elegir restricciones incompatibles, identificadores con ámbitos distintos o conceptos codificados de forma diferente. U3 y U4 resolverán capas que la estructura sola no puede cerrar.

El contrato de datos de U2 documenta para cada elemento: significado en lenguaje natural, ruta lógica, tipo, cardinalidad, reglas de ausencia, contexto, identificador o referencia, procedencia esperada y pruebas. Se incluyen casos positivos y negativos. El control más importante no es solo «el JSON valida», sino comprobar que una transformación no ha perdido una relación o convertido un estado desconocido en una falsa ausencia.

La evaluación de equivalencia se realiza campo por campo y relación por relación. Se distinguen pérdidas estructurales, pérdidas de contexto, pérdidas de identidad y pérdidas semánticas. Un mapeo puede ser técnicamente completo —todos los campos tienen destino— y aun así ser semánticamente inadecuado si fusiona conceptos distintos o elimina condiciones necesarias para interpretarlos.

El cierre de U2 produce un modelo lógico y un contrato de datos para un caso sintético derivado de U1. La unidad no certifica un esquema productivo ni un perfil FHIR, no asigna códigos SNOMED CT/LOINC/ICD y no diseña una API. U3 estudiará terminologías, U4 interoperabilidad, U5 gobernanza y U6 pruebas de conformidad e implementación.

Puntos de integración

  • Restricciones convierten un modelo general en un contrato más específico para un contexto de uso definido.
  • Arquetipos separan restricciones de dominio del modelo de referencia y pueden evolucionar independientemente.
  • Mayor restricción estructural no garantiza por sí sola equivalencia semántica entre organizaciones.
  • Un contrato de datos debe especificar significado, tipo, cardinalidad, ausencia, contexto, identidad, procedencia y pruebas.
  • Mapeo completo de campos no equivale a mapeo semánticamente correcto ni a interoperabilidad demostrada.
  • U2 termina en modelo y contrato; terminologías, transporte, gobernanza y conformidad se validan en unidades posteriores.

Ejemplos y casos resueltos

Misma etiqueta, distinto significado

Situación. Dos tablas sintéticas contienen una columna status. En una describe el estado de un encuentro y en otra el estado de verificación de una condición.

Razonamiento paso a paso

  1. Identificar la entidad propietaria de cada campo.
  2. Escribir una definición de cada status.
  3. Comparar tipos y valores permitidos.
  4. Comprobar el contexto de la ruta lógica.
  5. Rechazar un mapeo uno-a-uno basado solo en el nombre.

Interpretación. La igualdad de etiquetas no establece equivalencia semántica; el contexto de la entidad y la definición forman parte del significado.

Cardinalidad que se pierde al aplanar

Situación. Un registro sintético contiene tres identificadores válidos de un paciente, pero una exportación CSV conserva solo el primero.

Razonamiento paso a paso

  1. Determinar la cardinalidad del elemento origen.
  2. Identificar que el destino permite una sola ocurrencia.
  3. Registrar la pérdida estructural.
  4. Evaluar si los otros identificadores tienen sistemas distintos.
  5. Rediseñar el destino como colección o tabla relacionada.

Interpretación. Un mapeo puede copiar un valor correctamente y aun así ser incompleto si destruye la cardinalidad de la fuente.

Valor sin contexto temporal

Situación. Una observación sintética de 120 aparece en un almacén sin tiempo clínico, aunque conserva fecha de carga.

Razonamiento paso a paso

  1. Distinguir valor, unidad y tiempo clínico.
  2. Separar fecha de carga del momento de medición.
  3. Comprobar si el origen conserva el tiempo efectivo.
  4. Clasificar la pérdida como pérdida de contexto.
  5. Evitar ordenar clínicamente el evento por la fecha de carga.

Interpretación. La estructura puede ser sintácticamente válida pero insuficiente para reconstruir la cronología clínica.

Identificador coincidente en dos ámbitos

Situación. Dos laboratorios sintéticos usan el identificador 00421 para muestras distintas.

Razonamiento paso a paso

  1. Separar value del sistema emisor.
  2. Documentar el namespace o ámbito de cada laboratorio.
  3. Construir una clave lógica compuesta por sistema y valor.
  4. Comprobar vigencia y asignador si existen.
  5. Evitar fusionar las muestras por coincidencia del valor.

Interpretación. Un identificador sin ámbito puede ser ambiguo; la unicidad depende del sistema en que fue emitido.

Esquema válido, significado incorrecto

Situación. Una transformación sintética produce JSON que valida contra el esquema, pero coloca la fecha de registro en el campo destinado al tiempo clínicamente relevante.

Razonamiento paso a paso

  1. Confirmar que el tipo dateTime es formalmente válido.
  2. Comparar definiciones semánticas de origen y destino.
  3. Detectar que el mapeo conserva tipo pero cambia significado.
  4. Clasificar el fallo como pérdida semántica.
  5. Añadir una prueba de contrato que compare el significado del campo, no solo el tipo.

Interpretación. La validación estructural no sustituye una validación de significado y trazabilidad del mapeo.

Actividad aplicada

Diseño y prueba de un modelo lógico para un episodio sintético

Procedimiento

  1. Reutiliza exclusivamente el episodio sintético construido en U1; no introduzcas datos clínicos reales ni identificables.
  2. Construye primero un modelo conceptual con sujeto, encuentro, problema, solicitud, observación e informe antes de elegir tipos o formatos.
  3. Transforma el modelo conceptual en un modelo lógico con elementos, rutas, tipos y cardinalidades explícitas.
  4. Documenta para cada dato las reglas de ausencia y distingue faltante, desconocido, no aplicable y ausencia documentada cuando corresponda.
  5. Representa contexto temporal y asistencial mediante elementos o relaciones explícitas; no dependas del orden de las filas.
  6. Define identificadores con sistema, valor, asignador o vigencia cuando sean relevantes y separa identificador de negocio de identificador técnico.
  7. Añade referencias tipadas y especifica cómo se resolverían; no unas entidades por coincidencia de cadenas sin ámbito.
  8. Conserva identidad, versión y procedencia como conceptos separados.
  9. Diseña al menos tres restricciones o arquetipos conceptuales y crea controles positivos y negativos para cada uno.
  10. Cierra con un contrato de datos que declare qué valida U2 y qué queda explícitamente para terminologías U3, interoperabilidad U4, gobernanza U5 y conformidad U6.

Problemas y tareas

  • Dibuja el modelo conceptual del episodio sintético de U1.
  • Clasifica cada entidad como independiente, embebida o referenciada y justifica la decisión.
  • Define la ruta lógica de quince elementos.
  • Asigna tipos de dato a esos elementos y explica tres alternativas descartadas.
  • Define cardinalidades mínimas y máximas para diez elementos o relaciones.
  • Detecta una pérdida causada por convertir una colección repetible en un único campo.
  • Representa dato faltante, desconocido, no aplicable y ausencia documentada sin usar números centinela.
  • Modela cantidad y unidad sin separar su significado.
  • Representa sujeto, encuentro y autor como contexto explícito.
  • Representa tiempo clínico, autoría y registro como marcas temporales diferentes.
  • Define una relación tipada entre solicitud y resultado.
  • Define una relación que no pueda resolverse y marca su incertidumbre.
  • Crea tres identificadores de negocio con ámbitos distintos.
  • Crea un identificador técnico de representación y explica por qué no sustituye al identificador de negocio.
  • Detecta una colisión de identificadores y evita una fusión incorrecta.
  • Representa dos versiones de la misma entidad manteniendo identidad persistente.
  • Añade procedencia a una transformación de unidad o consolidación.
  • Diseña un control negativo de cardinalidad.
  • Diseña un control negativo de tipo de dato.
  • Diseña un control negativo de referencia inexistente.
  • Construye una restricción o arquetipo conceptual para un resultado de laboratorio sintético.
  • Compara una instancia estructuralmente válida pero semánticamente incorrecta con una instancia correcta.
  • Construye una matriz origen→destino y clasifica pérdidas estructurales, de contexto, identidad o semántica.
  • Redacta el contrato de datos final y las pruebas que permiten auditarlo.

Entregables

  • Diagrama conceptual de entidades y relaciones.
  • Modelo lógico con rutas, tipos y cardinalidades.
  • Diccionario de reglas de ausencia.
  • Tabla de contexto clínico y temporal.
  • Registro de identificadores y namespaces.
  • Mapa de referencias y reglas de resolución.
  • Modelo de identidad, versiones y procedencia.
  • Tres restricciones o arquetipos conceptuales.
  • Suite de controles positivos y negativos.
  • Matriz origen→destino con clasificación de pérdidas.
  • Contrato de datos auditable.
  • Informe de fronteras U2→U3–U6.

Criterios de comprobación

  • Modelo conceptual y modelo lógico se presentan como capas distintas.
  • La serialización no se confunde con el modelo de información.
  • Cada elemento principal tiene definición, ruta, tipo y cardinalidad.
  • Los elementos repetibles no se aplanan sin documentar pérdida.
  • Dato faltante y ausencia documentada permanecen diferenciados.
  • Desconocido y no aplicable no usan el mismo valor sentinela.
  • Cantidad y unidad permanecen vinculadas.
  • Sujeto y encuentro forman parte explícita del contexto.
  • Tiempo clínico y tiempo de registro no se sustituyen mutuamente.
  • Las relaciones declaran dirección y significado.
  • Cada identificador de negocio declara su ámbito o sistema.
  • Identificador técnico y de negocio se mantienen separados.
  • Las referencias tienen una regla de resolución definida o se marcan como no resueltas.
  • La coincidencia de cadenas no basta para fusionar identidades.
  • La identidad de una entidad permanece estable entre versiones.
  • La procedencia identifica la transformación que produjo datos derivados.
  • Al menos un control positivo demuestra aceptación de una instancia conocida.
  • Al menos tres controles negativos demuestran detección de fallos previstos.
  • Las restricciones están vinculadas a requisitos y no se añaden de forma arbitraria.
  • El contrato diferencia conformidad estructural de equivalencia semántica.
  • La matriz detecta pérdidas de estructura, contexto, identidad y significado.
  • Un JSON válido no se presenta como prueba de interoperabilidad clínica.
  • No se introducen códigos SNOMED CT, LOINC o ICD como contenido central de U2.
  • No se implementan APIs o mensajería HL7 como contenido central de U2.
  • Todo el ejercicio usa información sintética y declara las fronteras con U3–U6.

Errores frecuentes y autoevaluación

Errores frecuentes y corrección

  • Confundir modelo de información con esquema JSON.

    Separa semántica, modelo lógico y serialización; un esquema es solo una representación de parte de las restricciones.

  • Diseñar columnas antes de definir entidades y relaciones.

    Construye primero el modelo conceptual y después decide estructura lógica y física.

  • Guardar todo como texto.

    Usa tipos que preserven fechas, cantidades, identificadores y relaciones cuando el significado lo requiera.

  • Tratar 0..1 y 0..* como equivalentes porque ambos son opcionales.

    Cardinalidad distingue obligatoriedad y repetición; documenta mínimo y máximo.

  • Codificar desconocido como cero.

    Usa una representación explícita de ausencia o desconocimiento; cero puede ser un valor clínico real.

  • Usar cadena vacía como ausencia documentada.

    Diferencia falta de dato de negación explícita.

  • Separar valor y unidad sin relación verificable.

    Modela la cantidad como una estructura coherente o conserva una asociación inequívoca.

  • Confiar en el nombre del campo para mapear conceptos.

    Compara definición, entidad, ruta, tipo, cardinalidad y contexto.

  • Copiar contexto en texto libre en cada fila.

    Representa entidades y referencias cuando el contexto necesita identidad y actualización consistente.

  • Usar una relación genérica para todos los enlaces.

    Declara tipo y dirección de la relación.

  • Tratar un identificador como globalmente único sin namespace.

    Conserva sistema emisor, ámbito y valor.

  • Confundir identificador técnico de recurso con número clínico de negocio.

    Modela ambas identidades por separado y documenta su relación.

  • Fusionar entidades porque comparten el mismo valor de identificador.

    Comprueba el sistema o ámbito antes de decidir identidad.

  • Sobrescribir versiones.

    Mantén identidad persistente y estados versionados con procedencia cuando el caso lo requiera.

  • Usar procedencia como sinónimo de versionId.

    El versionado identifica estados; la procedencia describe agentes y actividades que los produjeron.

  • Creer que un esquema válido garantiza significado correcto.

    Añade pruebas de mapeo, contexto, identidad y equivalencia semántica.

  • Suponer que un arquetipo o perfil resuelve la terminología.

    La estructura puede restringir dónde va un código, pero U3 debe validar el sistema terminológico y el concepto.

  • Presentar un contrato local como interoperabilidad demostrada.

    U4 debe probar transporte, perfiles, APIs y comportamiento entre sistemas reales o simulados.

1. ¿Qué diferencia un modelo lógico de una serialización?

Respuesta: El modelo lógico define entidades, elementos, tipos y relaciones; la serialización codifica una instancia de ese modelo en un formato externo.

Razonamiento: JSON o XML pueden representar modelos diferentes y no contienen por sí solos toda la semántica.

Error que evita: Llamar modelo al archivo JSON.

2. ¿Una instancia que valida contra un esquema es clínicamente correcta?

Respuesta: No necesariamente.

Razonamiento: El esquema puede comprobar estructura sin detectar un valor, unidad, identidad o concepto incorrecto.

Error que evita: Equiparar conformidad estructural con validez clínica.

3. ¿Qué expresa 0..*?

Respuesta: Que un elemento puede faltar o repetirse un número no acotado de veces dentro de las reglas del modelo.

Razonamiento: Combina mínimo cero con máximo múltiple.

Error que evita: Interpretarlo solo como opcional.

4. ¿Por qué no conviene guardar desconocido como cero?

Respuesta: Porque cero puede ser un valor real y se pierde la distinción entre dato observado y dato ausente.

Razonamiento: La ausencia necesita semántica propia.

Error que evita: Usar valores centinela sin contrato.

5. ¿Dos campos llamados status son equivalentes?

Respuesta: No por el nombre solamente.

Razonamiento: Debe compararse la entidad, definición, ruta, valores y contexto.

Error que evita: Mapeo por coincidencia de etiquetas.

6. ¿Qué diferencia identificador de negocio de identificador técnico?

Respuesta: El primero identifica una entidad dentro de un proceso o ámbito de negocio; el segundo identifica una representación dentro de una plataforma técnica.

Razonamiento: Ambos pueden coexistir y tener ciclos de vida distintos.

Error que evita: Usar el id técnico como identidad clínica universal.

7. ¿El valor 00421 identifica una entidad de forma global?

Respuesta: No sin conocer su sistema o ámbito emisor.

Razonamiento: El mismo valor puede reutilizarse en namespaces distintos.

Error que evita: Ignorar el namespace.

8. ¿Qué diferencia versión de procedencia?

Respuesta: La versión identifica un estado; la procedencia documenta agentes, actividades y entidades relacionadas con su creación o transformación.

Razonamiento: Son capas complementarias.

Error que evita: Reducir procedencia a versionId.

9. ¿Qué aporta un arquetipo?

Respuesta: Restricciones de dominio aplicadas sobre un modelo de referencia.

Razonamiento: Permite especificar contenido clínico sin rediseñar las clases básicas.

Error que evita: Tratar el arquetipo como una base de datos o terminología.

10. ¿Un mapeo que cubre el 100 % de campos es necesariamente semánticamente completo?

Respuesta: No.

Razonamiento: Puede mapear campos a destinos con significado diferente o eliminar contexto y relaciones.

Error que evita: Medir calidad solo por porcentaje de campos mapeados.

11. ¿Qué debe contener un contrato de datos auditable?

Respuesta: Definiciones, tipos, cardinalidades, ausencia, contexto, identidad, procedencia, restricciones y pruebas vinculadas al uso.

Razonamiento: El contrato debe permitir verificar tanto estructura como transformaciones relevantes.

Error que evita: Limitarlo a nombres y tipos de columnas.

12. ¿Qué demuestra dominio de U2?

Respuesta: Poder diseñar y probar un modelo lógico que preserve estructura, contexto, identidad, versión y procedencia, declarando pérdidas y fronteras con terminología e interoperabilidad.

Razonamiento: La competencia central es preservar significado mediante estructura verificable.

Error que evita: Memorizar nombres de clases de un estándar sin justificar el modelo.

Glosario disciplinar

  • Modelo de información

    Representación explícita de entidades, elementos, relaciones, tipos y restricciones usada para dar estructura computable a información.

  • Modelo conceptual

    Representación de conceptos y relaciones del dominio independiente de decisiones concretas de almacenamiento o serialización.

  • Modelo lógico

    Especificación computable de entidades, elementos, tipos, cardinalidades y relaciones sin fijar necesariamente la implementación física.

  • Modelo físico

    Diseño concreto de almacenamiento, tablas, índices, documentos u otras estructuras de persistencia.

  • Modelo de referencia

    Conjunto general y relativamente estable de clases y reglas sobre el que pueden imponerse restricciones de dominio.

  • Instancia

    Conjunto concreto de datos que pretende satisfacer las reglas de un modelo.

  • Serialización

    Representación externa de una instancia en un formato como JSON o XML.

  • Entidad

    Objeto conceptual distinguible que posee identidad o participa en relaciones del modelo.

  • Elemento

    Unidad definida dentro de una estructura con ruta, tipo, cardinalidad y reglas de uso.

  • Ruta lógica

    Ubicación de un elemento dentro de una jerarquía o estructura de información.

  • Tipo de dato

    Conjunto de valores y operaciones permitidas para un elemento, como fecha, cantidad, texto, identificador o referencia.

  • Cardinalidad

    Número mínimo y máximo de ocurrencias permitidas para un elemento o relación.

  • Obligatoriedad

    Regla que exige la presencia de un elemento bajo las condiciones definidas.

  • Repetición

    Capacidad de un elemento o relación para aparecer más de una vez.

  • Dato faltante

    Información no disponible en el conjunto observado, sin implicar automáticamente ausencia clínica.

  • Ausencia documentada

    Representación explícita de que un fenómeno o valor no estaba presente, diferente de un campo no informado.

  • Valor desconocido

    Estado en que se sabe que debería existir una respuesta pero su valor no es conocido.

  • No aplicable

    Estado en que una pregunta o elemento no corresponde al caso concreto.

  • Restricción

    Regla que reduce el conjunto de instancias permitidas por un modelo más general.

  • Invariante

    Condición lógica que debe cumplirse para que una instancia sea considerada válida bajo una especificación.

  • Contexto clínico

    Información sobre sujeto, encuentro, tiempo, autor, método y otras condiciones necesarias para interpretar un dato.

  • Relación tipada

    Enlace cuya dirección y significado están explícitamente definidos.

  • Referencia

    Mecanismo para señalar otra entidad o representación sin copiar necesariamente todo su contenido.

  • Embebido

    Contenido almacenado dentro de la estructura del objeto que lo contiene en lugar de ser referenciado como entidad independiente.

  • Identificador

    Valor asignado para distinguir una entidad dentro de un ámbito definido.

  • Identificador de negocio

    Identificador usado por un proceso o dominio externo al mecanismo técnico de almacenamiento o transporte.

  • Identificador técnico

    Identificador de una representación o recurso dentro de una plataforma o sistema técnico.

  • Sistema de identificadores

    Ámbito o namespace que da significado y unicidad contextual al valor de un identificador.

  • Asignador

    Organización o autoridad que emite o administra un identificador.

  • Resolución de referencia

    Proceso por el cual una referencia o identificador se vincula con la entidad representada.

  • Integridad referencial

    Propiedad por la que los enlaces entre entidades cumplen las reglas de existencia y destino definidas por el modelo.

  • Versión

    Estado identificable de una entidad o representación dentro de su historia de cambios.

  • Versionado

    Mecanismo para conservar y relacionar estados sucesivos de información.

  • Procedencia

    Información sobre agentes, entidades y actividades que participaron en la creación o transformación de datos.

  • Auditoría de transformación

    Registro que permite reconstruir cómo datos de origen produjeron una representación derivada.

  • Mapa origen-destino

    Correspondencia explícita entre elementos de una fuente y elementos de una representación transformada.

  • Arquetipo

    Definición formal de restricciones de dominio aplicada sobre un modelo de referencia.

  • Plantilla

    Composición o restricción adicional de modelos o arquetipos para un contexto de uso específico.

  • Contrato de datos

    Especificación verificable de estructura, significado, tipos, cardinalidades, contexto, identidad y reglas esperadas para un intercambio o transformación.

  • Esquema

    Representación formal de una estructura y parte de sus restricciones sintácticas o lógicas.

  • Conformidad estructural

    Cumplimiento de las reglas de estructura y restricciones comprobadas por un esquema o validador.

  • Equivalencia semántica

    Propiedad de dos representaciones que conservan el mismo significado relevante para el uso definido.

  • Pérdida estructural

    Eliminación o alteración de elementos, cardinalidades o relaciones durante una transformación.

  • Pérdida de contexto

    Eliminación de información necesaria sobre sujeto, tiempo, encuentro, método u otras condiciones de interpretación.

  • Pérdida de identidad

    Alteración o ambigüedad que impide saber si dos registros representan la misma entidad.

  • Pérdida semántica

    Transformación que conserva forma aparente pero modifica o elimina significado relevante.

  • Validación estructural

    Comprobación de que una instancia satisface reglas formales del modelo o esquema.

  • Control positivo

    Instancia diseñada para cumplir las reglas y demostrar que el validador acepta un caso conocido.

  • Control negativo

    Instancia deliberadamente inválida usada para comprobar que una regla detecta un fallo esperado.

  • Dos niveles de modelado

    Arquitectura que separa un modelo de referencia estable de restricciones o definiciones de dominio que evolucionan de forma independiente.

Cierre de la unidad

Modelar información clínica sin pérdida accidental de significado mediante una separación explícita entre modelo de referencia y contenido clínico, definiendo entidades, elementos, tipos de dato, cardinalidades, contexto, identificadores, referencias, versiones, procedencia y restricciones. La unidad reutiliza la semántica longitudinal de U1 y prepara la codificación terminológica de U3 y la interoperabilidad de U4, sin confundir una estructura válida con equivalencia semántica, conformidad de intercambio o utilidad clínica. Conecta especialmente con Ingeniería de datos clínicos: ETL y almacenes longitudinales necesitan modelos explícitos de cardinalidad, contexto, identidad y versionado para evitar pérdidas silenciosas, Interoperabilidad semántica: La estructura correcta es una condición necesaria pero no suficiente; U3 y U4 añaden terminología y transporte interoperable, Sistemas de ayuda a la decisión: Reglas clínicas dependen de tipos, estados, referencias y contexto coherentes; un campo mal modelado puede activar lógica sobre información incorrecta, Investigación con HCE: Transformaciones que cambian unidades, tiempos o identidad pueden introducir sesgo antes de cualquier análisis estadístico. Material educativo en estado review y basado exclusivamente en datos sintéticos. No constituye diseño de una HCE productiva, perfil FHIR, arquetipo clínico aprobado, especificación contractual para un proveedor, asesoría regulatoria, validación de interoperabilidad ni decisión clínica. Los estándares se usan para enseñar principios de modelado y sus ediciones deben verificarse para cualquier implementación real. U2 no asigna terminologías clínicas ni demuestra equivalencia semántica entre sistemas; esas capas se desarrollan y prueban en U3–U6. No se deben introducir datos identificables de pacientes.
