Desarrollo 1

1. De palabras a significados computables: terminologías, clasificaciones y contexto

Un término clínico visible en pantalla no es necesariamente un concepto único. La misma frase puede ser ambigua, depender del idioma o abreviarse localmente. Una terminología controlada intenta asociar significados identificables con códigos estables y reglas explícitas; el texto de presentación ayuda a las personas, pero no debe sustituir al identificador y al sistema que fijan el significado computable.

Conviene separar terminología, nomenclatura y clasificación. Una terminología como SNOMED CT busca representar significados clínicos con granularidad y relaciones formales. Una clasificación como ICD-11 organiza entidades en categorías adecuadas para finalidades estadísticas y de reporte. Ninguna de estas funciones implica que un sistema sea universalmente «mejor»: la elección depende del propósito de registro, recuperación, análisis o reporte.

En informática sanitaria también se distinguen code system y value set. El code system define un universo de códigos y su significado; un value set selecciona los códigos permitidos para un contexto concreto. En FHIR, los bindings conectan elementos con value sets, pero el detalle de esos bindings y su validación pertenece a U4. U3 se concentra en comprender qué significa seleccionar y versionar contenido terminológico.

El contexto sigue siendo parte del significado. Codificar «dolor» sin distinguir si es síntoma actual, antecedente familiar, hallazgo negado o razón de consulta puede conservar una palabra y perder la afirmación clínica. La estructura contextual aprendida en U2 debe envolver al código: sujeto, evento, estado, tiempo y rol del dato no desaparecen porque exista una terminología.

Todo registro terminológico reproducible debe conservar al menos sistema, código, versión cuando sea relevante, display utilizado y concepto local de origen. El código sin sistema puede colisionar con otro vocabulario; el sistema sin versión dificulta reconstruir cambios; y el display no debe usarse como llave estable. Para análisis longitudinales se necesita saber qué edición estaba vigente cuando se realizó el mapeo.

La competencia central de U3 no es memorizar códigos. Es justificar una elección terminológica y mostrar qué información se preserva, qué se simplifica y qué queda incierto. U2 aportó estructura, identificadores y procedencia; U3 aporta semántica controlada; U4 transportará después esa combinación entre sistemas.

Puntos de integración

  • El texto visible no sustituye al identificador terminológico.
  • Terminología y clasificación resuelven problemas distintos de representación.
  • Un code system define códigos; un value set restringe su uso.
  • El contexto clínico debe acompañar al código seleccionado.
  • Versionar terminologías permite reconstruir decisiones y cambios semánticos.
  • U3 modela significado; U4 abordará transporte y bindings interoperables.

Desarrollo 2

2. SNOMED CT: conceptos, descripciones, relaciones y expresiones

SNOMED CT es conceptocéntrica. Cada concepto representa un significado clínico y posee un identificador numérico que no lleva significado humano intrínseco. Las descripciones proporcionan formas legibles, entre ellas Fully Specified Name y sinónimos. Por tanto, concepto, concept identifier y descripción son componentes distintos: cambiar un término preferido no convierte automáticamente el concepto en otro.

Las relaciones organizan y definen conceptos. La relación is a construye jerarquías de subtipo, mientras atributos como finding site o associated morphology aportan características definitorias en dominios permitidos. El Concept Model fija dominios, rangos, cardinalidades y agrupaciones válidas, evitando combinar atributos de forma arbitraria.

La definición lógica permite distinguir conceptos más generales de otros más específicos y realizar inferencias de subsunción. Sin embargo, navegar por la jerarquía no demuestra que un concepto sea apropiado para un caso concreto. La selección clínica necesita evidencia del escenario, no solo que el término esté disponible como descendiente de otro.

Los Reference Sets —refsets— permiten representar subconjuntos, preferencias lingüísticas, value sets y también mapas hacia otros sistemas. Un refset no cambia necesariamente la definición de los conceptos que contiene; añade una capa de configuración o información derivada para un uso determinado. Por eso debe registrarse también qué refset, edición y fecha efectiva se utilizaron.

SNOMED CT admite pre-coordinación y postcoordinación. Un concepto precoordinado ya representa el significado requerido; una expresión postcoordinada combina conceptos y atributos siguiendo la gramática y el Concept Model. La postcoordinación aumenta expresividad, pero no autoriza combinaciones libres ni garantiza que todos los sistemas receptores puedan procesarlas de la misma forma.

La edición internacional de SNOMED CT evoluciona mediante releases versionadas. Esta unidad fija la International Edition de agosto de 2026, con fecha efectiva 20260801 y estado de producción, como versión de referencia para los ejercicios. El estudiante no escribe simplemente «SNOMED CT»: registra edición y fecha efectiva y evita asumir que un código activo, una descripción o una relación permanecerán idénticos entre releases.

Puntos de integración

  • Concepto, identificador y descripción SNOMED CT son entidades diferentes.
  • Las relaciones lógicas sostienen jerarquías y definiciones computables.
  • El Concept Model restringe atributos, dominios, rangos y cardinalidades.
  • Los refsets configuran subconjuntos, preferencias y mapas para usos concretos.
  • La postcoordinación debe respetar gramática y reglas del modelo.
  • Cada mapeo SNOMED CT debe registrar edición y versión utilizadas.

Desarrollo 3

3. LOINC: identificar qué observación o prueba se está nombrando

LOINC se diseñó para identificar observaciones, mediciones, documentos y otros elementos clínicos mediante códigos estables. Un código LOINC no debe seleccionarse porque su Long Common Name «se parece» al nombre local. La equivalencia depende de los atributos que definen el término y de la información disponible en el sistema de origen.

El Fully-Specified Name de un término LOINC se construye con cinco o seis partes principales: Component, Property, Time, System, Scale y, cuando corresponde, Method. Estas partes responden preguntas diferentes: qué se observa, qué propiedad se expresa, durante qué intervalo, en qué sistema o muestra, con qué tipo de escala y mediante qué método cuando éste forma parte del significado.

Component no equivale por sí solo al nombre de la prueba. Dos términos pueden medir el mismo analito y diferir en Property, System, Scale o Method. Del mismo modo, dos pruebas locales con rótulos diferentes pueden representar el mismo LOINC si sus atributos definitorios son equivalentes. El mapeo debe comparar atributos, no cadenas de texto aisladas.

Las unidades son un control importante, pero no sustituyen a Property ni Scale. Una unidad incompatible puede revelar un mapeo erróneo; una unidad compatible no demuestra por sí sola equivalencia. Cuando el origen omite muestra, método u otra característica definitoria, la respuesta correcta puede ser «información insuficiente» en vez de elegir el candidato más parecido.

LOINC también está versionado. La versión 2.83 fue publicada el 19 de agosto de 2026 y añadió y actualizó contenido en varios dominios. El código LOINC es un identificador permanente, pero estados, nombres y contenido asociado pueden evolucionar; por ello los procesos reproducibles conservan la versión y revisan conceptos active, discouraged o deprecated según las reglas vigentes.

U3 usa LOINC para entrenar razonamiento de mapeo, no para construir una interfaz de laboratorio. Se conserva código local, definición local, atributos observados, LOINC candidato, versión, evidencia y grado de equivalencia. El transporte de esos códigos en mensajes y recursos FHIR pertenece a U4.

Puntos de integración

  • LOINC se selecciona por atributos, no por similitud textual.
  • Component, Property, Time, System, Scale y Method son dimensiones distintas.
  • Una unidad compatible ayuda a validar pero no prueba equivalencia.
  • La ausencia de un atributo crítico puede impedir un mapeo seguro.
  • Versionar LOINC conserva trazabilidad frente a cambios de contenido.
  • U3 mapea significados; U4 transportará códigos entre sistemas.

Desarrollo 4

4. ICD-11: Foundation, MMS y finalidad clasificatoria

ICD-11 pertenece a la familia de clasificaciones de la OMS y no debe tratarse como un reemplazo directo de SNOMED CT. La Foundation Component es una colección multidimensional de entidades interconectadas y permite múltiples padres. A partir de esa Foundation se derivan linearizaciones diseñadas para usos específicos.

La linearización ICD-11 for Mortality and Morbidity Statistics —MMS— organiza categorías para codificación estadística de mortalidad y morbilidad. Una linearización impone decisiones de estructura y exclusividad que facilitan tabulación. Esa finalidad es distinta de representar toda la granularidad clínica necesaria para documentación o recuperación semántica.

El hecho de que una entidad exista en la Foundation no implica que su posición o código estadístico se use igual en MMS. El estudiante debe registrar si trabaja con Foundation o con una linearización concreta, además de la release. Mezclar identificadores de Foundation y códigos MMS sin declarar la capa produce errores difíciles de auditar.

ICD-11 permite mayor expresividad mediante extension codes y mecanismos de postcoordinación en contextos definidos. Aun así, la codificación estadística tiene reglas y convenciones propias. U3 no enseña codificación profesional para facturación, mortalidad o reporte legal; utiliza escenarios sintéticos para comprender cómo una clasificación transforma significado clínico en categorías de reporte.

Mapear SNOMED CT hacia ICD no es una sustitución carácter por carácter. Un concepto clínico muy específico puede corresponder a una categoría más amplia, requerir reglas adicionales o no tener equivalencia uno-a-uno. Los mapas publicados pueden contener reglas, advice y dependencias contextuales; por ello «existe un mapa» no equivale a «los sistemas son semánticamente idénticos».

El ICD-11 Browser 2026-01 proporciona la release vigente para MMS consultada en esta unidad. Los ejercicios registran release, entidad/categoría, propósito y pérdidas de granularidad. U5 y U6 podrán tratar después gobernanza, auditoría e implementación; U3 se limita a la semántica y al mapeo.

Puntos de integración

  • La Foundation ICD-11 es multidimensional y admite múltiples padres.
  • MMS es una linearización destinada a estadísticas de morbilidad y mortalidad.
  • Foundation y MMS no deben mezclarse como si fueran la misma capa.
  • Los extension codes amplían representación dentro de reglas definidas.
  • Mapear SNOMED CT a ICD puede implicar pérdida o reglas contextuales.
  • La release ICD utilizada debe quedar registrada en toda auditoría.

Desarrollo 5

5. Mapeo, equivalencia, versiones y validación terminológica

Un mapeo terminológico vincula una expresión o código de origen con uno o más destinos para un propósito definido. Antes de mapear se documentan el significado del origen, sistema y versión, contexto de uso y atributos relevantes. El objetivo no es maximizar el porcentaje de códigos asignados, sino minimizar pérdida semántica no declarada.

La relación de equivalencia debe expresarse. Un mapeo puede ser exacto, origen más amplio, origen más estrecho, parcialmente solapado o sin correspondencia adecuada. Las etiquetas exactas dependen del marco empleado, pero el principio es estable: una flecha origen→destino sin tipo de relación oculta información crítica.

Los mapas pueden ser direccionales. Que A se mapee a B para un propósito no garantiza que B permita reconstruir A ni que el mapa inverso sea válido. Esta asimetría es especialmente importante al pasar de una terminología clínica granular a una clasificación estadística. La pérdida debe documentarse y, cuando sea relevante, cuantificarse por casos y no solo por cobertura global.

La validación combina controles positivos, negativos y casos ambiguos. Un control positivo debe tener una correspondencia conocida; un negativo debe demostrar que el procedimiento puede rechazar candidatos incompatibles; un caso ambiguo obliga a registrar incertidumbre o solicitar información adicional. La revisión por un segundo mapeador puede detectar decisiones frágiles, pero el acuerdo entre personas no convierte una equivalencia incorrecta en verdadera.

Versiones y estado de conceptos forman parte del producto. Un código puede permanecer identificable mientras cambian descripciones, estado o relaciones; otro puede inactivarse y requerir asociaciones históricas o sustitutos. El registro de mapeo conserva fecha, versión origen/destino, criterio, autor/revisor y razón de cada cambio para permitir mantenimiento.

El producto final de U3 es un registro de mapeo sintético auditable que integra la estructura de U2 con SNOMED CT, LOINC e ICD-11. Debe separar selección terminológica, clasificación y equivalencia; declarar pérdidas; y reservar para U4 la serialización FHIR/HL7, bindings, perfiles, APIs y pruebas de intercambio.

Puntos de integración

  • Todo mapeo necesita propósito, origen, destino y versión explícitos.
  • La relación de equivalencia debe documentarse, no suponerse.
  • Los mapas son direccionales y pueden perder granularidad.
  • Controles positivos, negativos y ambiguos prueban el procedimiento de mapeo.
  • Estados e inactivaciones exigen mantenimiento terminológico trazable.
  • U3 entrega semántica auditada antes de la interoperabilidad de U4.

Ejemplos y casos resueltos

Un código SNOMED CT no es su texto visible

Situación. Un sistema sintético muestra una descripción local que cambia de idioma mientras conserva el mismo concepto SNOMED CT.

Razonamiento paso a paso

  1. Separar concept identifier de display.
  2. Comprobar sistema y edición.
  3. Revisar Fully Specified Name y sinónimos permitidos.
  4. Mantener el contexto clínico fuera del display.
  5. Registrar cualquier cambio de descripción sin cambiar el concepto por defecto.

Interpretación. Un cambio de texto no implica un cambio de concepto cuando el identificador y el significado permanecen estables.

Dos pruebas de glucosa no son automáticamente el mismo LOINC

Situación. Dos códigos locales sintéticos dicen «glucosa», pero uno procede de plasma y otro de orina.

Razonamiento paso a paso

  1. Comparar Component.
  2. Comparar Property.
  3. Comparar Time.
  4. Comparar System.
  5. Revisar Scale, Method y unidades como controles.

Interpretación. La coincidencia del analito no basta; System y las demás partes pueden requerir códigos LOINC diferentes.

SNOMED CT clínico frente a ICD-11 estadístico

Situación. Un concepto clínico sintético muy específico debe resumirse para un informe estadístico.

Razonamiento paso a paso

  1. Identificar el propósito clínico del concepto origen.
  2. Determinar la linearización ICD-11 aplicable.
  3. Buscar correspondencia y reglas publicadas.
  4. Registrar pérdida de granularidad.
  5. No asumir que el destino permite reconstruir el origen.

Interpretación. El mapeo hacia una clasificación puede ser útil para reporte y aun así perder detalle clínico.

Código local ambiguo y decisión de no mapear

Situación. El código local LAB-17 solo contiene el texto «PCR», sin indicar analito, muestra ni método.

Razonamiento paso a paso

  1. Enumerar las interpretaciones posibles de la abreviatura.
  2. Identificar atributos definitorios ausentes.
  3. Evitar elegir el candidato más frecuente.
  4. Clasificar el caso como insuficientemente especificado.
  5. Solicitar metadatos adicionales y conservar el código local.

Interpretación. No mapear puede ser una decisión más rigurosa que asignar un código normalizado sin evidencia suficiente.

Cambio de versión y mantenimiento del mapa

Situación. Un mapa sintético fue creado con una release anterior y uno de los conceptos de destino aparece ahora inactivo.

Razonamiento paso a paso

  1. Identificar versión histórica y versión actual.
  2. Revisar estado y asociaciones históricas.
  3. Evaluar si existe sustituto apropiado.
  4. Volver a comprobar equivalencia en el contexto de origen.
  5. Registrar revisor, fecha, motivo y decisión.

Interpretación. Actualizar una terminología no autoriza sustituciones automáticas; cada cambio con impacto semántico debe revisarse.

Actividad aplicada

Auditoría terminológica de un registro clínico sintético

Procedimiento

  1. Trabaja únicamente con el dataset sintético proporcionado; no introduzcas datos identificables ni documentación clínica real.
  2. Conserva para cada elemento el código local, texto local, significado documentado, sistema destino, código destino, versión y display.
  3. Separa el contexto estructural de U2 de la selección terminológica: sujeto, encuentro, estado y tiempo no se sustituyen por un código.
  4. Para SNOMED CT diferencia concepto, identificador, descripción, relación y refset antes de analizar cualquier mapa.
  5. Para LOINC compara Component, Property, Time, System, Scale y Method; no mapees por coincidencia de nombre.
  6. Para ICD-11 declara si trabajas con Foundation o con MMS y registra la release.
  7. Clasifica cada correspondencia como exacta, más amplia, más estrecha, parcial, ambigua o sin correspondencia, justificando el criterio.
  8. Prueba al menos un control positivo, un control negativo y un caso deliberadamente ambiguo.
  9. Registra pérdidas semánticas y no uses cobertura de mapeo como sinónimo de exactitud.
  10. Compara versiones y estados terminológicos antes de cerrar el producto.
  11. Solicita revisión independiente para las decisiones de mayor impacto semántico.
  12. Cierra con fronteras: U4 transporta códigos y bindings; U5 gobierna acceso/auditoría; U6 valida implementación.

Problemas y tareas

  • Distingue en diez ejemplos texto libre, código local, code system, value set y clasificación.
  • Explica por qué dos displays iguales pueden no demostrar identidad semántica.
  • Separa concepto SNOMED CT, concept identifier y descripción en un ejemplo sintético.
  • Clasifica tres relaciones SNOMED CT como is a o atributo y explica su función.
  • Identifica qué información añadiría un refset sin modificar la definición central del concepto.
  • Compara pre-coordinación y postcoordinación en un escenario educativo sin crear una expresión clínica productiva.
  • Registra edición y fecha de SNOMED CT para todos los ejemplos.
  • Descompón seis términos LOINC en Component, Property, Time, System, Scale y Method.
  • Detecta dos falsos candidatos LOINC que coinciden en Component pero no en System.
  • Detecta un caso donde las unidades descartan un candidato pero no identifican por sí solas el correcto.
  • Declara un código local como no mapeable cuando falta un atributo LOINC crítico.
  • Registra la versión LOINC usada y comprueba estado de cada término candidato.
  • Distingue ICD-11 Foundation de MMS en cinco entidades sintéticas.
  • Explica por qué una entidad Foundation puede no equivaler a una categoría estadística MMS uno-a-uno.
  • Mapea un concepto clínico granular hacia una categoría más amplia y documenta la pérdida.
  • Demuestra por qué un mapa origen→destino no implica automáticamente un mapa destino→origen.
  • Clasifica diez pares como exactos, más amplios, más estrechos, parciales o no equivalentes.
  • Construye un control positivo con equivalencia conocida y define el resultado esperado.
  • Construye un control negativo que deba ser rechazado aunque el texto se parezca.
  • Construye un caso ambiguo y especifica qué dato resolvería la incertidumbre.
  • Calcula cobertura descriptiva del conjunto y explica por qué no mide exactitud semántica.
  • Revisa un concepto inactivo y documenta qué información adicional necesitas antes de reemplazarlo.
  • Realiza doble revisión de cinco mapeos y registra desacuerdos sin resolverlos por mayoría automática.
  • Construye el registro de mapeo final con trazabilidad y fronteras explícitas hacia U4–U6.

Errores frecuentes y autoevaluación

Errores frecuentes y corrección

  • Mapear por texto idéntico.

    Compara significado, atributos, sistema y contexto; la similitud textual solo genera candidatos.

  • Guardar solo el código sin sistema.

    Conserva code system y versión para identificar el significado de forma reproducible.

  • Usar el display como llave estable.

    El display es presentación humana y puede cambiar; usa identificadores del sistema.

  • Confundir SNOMED CT con una clasificación estadística.

    SNOMED CT representa significados clínicos granulares; ICD cumple además finalidades clasificatorias específicas.

  • Tratar un concepto SNOMED CT como su FSN.

    Concepto y descripción son componentes diferentes.

  • Asumir que cualquier relación SNOMED CT es is a.

    Distingue subtipo de atributos definitorios y otras relaciones.

  • Postcoordinar libremente términos SNOMED CT.

    Las expresiones deben respetar gramática y Concept Model.

  • Elegir LOINC solo por Component.

    Compara las seis partes definitorias aplicables.

  • Usar unidades iguales como prueba de LOINC equivalente.

    La unidad puede descartar incompatibilidades, pero no identifica sola el término.

  • Forzar un LOINC cuando falta la muestra.

    Registra insuficiencia de información y solicita el atributo faltante.

  • Tratar Foundation y MMS como sinónimos.

    Declara explícitamente la capa ICD-11 y su propósito.

  • Usar ICD-11 para reemplazar todo el detalle clínico.

    Documenta qué granularidad se pierde al clasificar.

  • Suponer que un mapa es bidireccional.

    Valida cada dirección por separado.

  • Llamar exacto a cualquier mapa existente.

    Clasifica equivalencia según significado y propósito, no por existencia de una flecha.

  • Maximizar cobertura aunque aumenten falsos mapeos.

    Prioriza exactitud y deja casos no resueltos cuando la evidencia es insuficiente.

  • Ignorar códigos inactivos.

    Revisa estado, asociaciones históricas y versión antes de mantener o sustituir.

  • Actualizar automáticamente a un supuesto sucesor.

    Comprueba que el nuevo concepto preserve el significado requerido.

  • Confundir codificación correcta con interoperabilidad completa.

    U3 cubre semántica; estructura, bindings, transporte y validación de intercambio requieren U2/U4.

1. ¿Por qué un código sin sistema es ambiguo?

Respuesta: Porque el mismo valor textual puede existir en sistemas distintos.

Razonamiento: El sistema forma parte de la identidad computable del código.

Error que evita: Tratar el valor del código como global.

2. ¿El FSN de SNOMED CT es el concepto?

Respuesta: No.

Razonamiento: Es una descripción no ambigua vinculada al concepto; el concepto tiene su propio identificador.

Error que evita: Confundir texto con significado identificado.

3. ¿Qué construye la jerarquía principal de SNOMED CT?

Respuesta: Las relaciones is a.

Razonamiento: Expresan relaciones de subtipo entre conceptos.

Error que evita: Tratar cualquier atributo como jerarquía.

4. ¿Para qué sirve un refset?

Respuesta: Para representar subconjuntos u otra información derivada como preferencias o mapas.

Razonamiento: Añade configuración o asociaciones sin redefinir necesariamente el concepto.

Error que evita: Pensar que todo refset es una nueva terminología.

5. ¿Qué seis dimensiones principales deben revisarse en LOINC?

Respuesta: Component, Property, Time, System, Scale y Method cuando aplica.

Razonamiento: La combinación determina el significado del término.

Error que evita: Mapear solo por analito.

6. ¿Unidades compatibles prueban que el LOINC es correcto?

Respuesta: No.

Razonamiento: Son una comprobación parcial; otras partes pueden diferir.

Error que evita: Usar unidades como criterio único.

7. ¿Foundation y MMS de ICD-11 son idénticas?

Respuesta: No.

Razonamiento: MMS es una linearización derivada de la Foundation para una finalidad concreta.

Error que evita: Mezclar entidades Foundation con códigos estadísticos.

8. ¿Un mapa SNOMED→ICD exacto en una dirección garantiza el inverso?

Respuesta: No.

Razonamiento: El mapeo puede perder granularidad y ser direccional.

Error que evita: Suponer reversibilidad.

9. ¿Qué significa dejar un caso sin correspondencia?

Respuesta: Que la evidencia no sostiene un destino adecuado para el propósito definido.

Razonamiento: La no asignación explícita evita fabricar equivalencia.

Error que evita: Forzar cobertura del 100 %.

10. ¿Por qué registrar versión?

Respuesta: Porque contenido, estados, descripciones y relaciones pueden cambiar entre releases.

Razonamiento: La versión permite reproducir la decisión terminológica.

Error que evita: Guardar solo fecha local.

11. ¿Cobertura alta demuestra mapeo exacto?

Respuesta: No.

Razonamiento: La cobertura indica cuántos elementos recibieron destino, no si el destino preserva significado.

Error que evita: Confundir cantidad con calidad.

12. ¿Qué demuestra dominio de U3?

Respuesta: Poder seleccionar y auditar códigos y mapas preservando sistema, versión, contexto, equivalencia, pérdidas e incertidumbre.

Razonamiento: La competencia es justificar significado y límites, no memorizar códigos.

Error que evita: Recitar nombres de terminologías sin poder auditar un mapa.

Glosario disciplinar

  • Terminología clínica

    Sistema organizado de conceptos y términos destinado a representar significado clínico de forma controlada.

  • Nomenclatura

    Sistema de nombres regulados para entidades de un dominio; su función puede ser más estrecha que la de una terminología ontológica.

  • Clasificación

    Sistema que agrupa entidades en categorías para finalidades como tabulación, estadísticas o reporte.

  • Code system

    Sistema que define códigos, sus significados, propiedades y reglas de mantenimiento.

  • Value set

    Conjunto de códigos seleccionados de uno o más code systems para un contexto de uso.

  • Código

    Identificador que representa una entidad dentro de un sistema definido.

  • Display

    Texto legible asociado a un código para presentación humana; no es una llave estable universal.

  • Versión terminológica

    Edición identificable del contenido de una terminología o clasificación.

  • Concepto SNOMED CT

    Significado clínico identificado de forma única dentro de SNOMED CT.

  • Concept identifier

    Identificador numérico de un concepto SNOMED CT sin significado humano intrínseco.

  • Descripción SNOMED CT

    Asociación entre un concepto y un término humano de un tipo determinado.

  • Fully Specified Name

    Descripción SNOMED CT destinada a expresar de forma no ambigua el significado de un concepto.

  • Sinónimo SNOMED CT

    Descripción alternativa legítima vinculada a un concepto.

  • Relación is a

    Relación de subtipo que organiza la jerarquía SNOMED CT.

  • Atributo SNOMED CT

    Tipo de relación utilizado para representar una característica definitoria.

  • Concept Model

    Reglas que delimitan atributos, dominios, rangos, cardinalidades y agrupaciones permitidas en SNOMED CT.

  • Reference Set

    Formato SNOMED CT para subconjuntos y metadatos derivados como preferencias, value sets o mapas.

  • Pre-coordinación

    Representación de un significado mediante un concepto ya existente.

  • Postcoordinación

    Representación mediante una expresión que combina conceptos y atributos según reglas de SNOMED CT.

  • Expresión SNOMED CT

    Combinación formal de conceptos y refinamientos que representa un significado clínico.

  • LOINC

    Terminología de identificadores para observaciones, pruebas, documentos y otros elementos clínicos.

  • LOINC code

    Identificador permanente asignado a un término LOINC.

  • Component

    Parte LOINC que identifica principalmente el analito, entidad o fenómeno observado.

  • Property

    Parte LOINC que expresa la propiedad medida u observada.

  • Time

    Parte LOINC que representa el aspecto temporal de la observación.

  • System

    Parte LOINC que identifica el sistema, muestra o contexto material observado.

  • Scale

    Parte LOINC que describe el tipo de escala, por ejemplo cuantitativa u ordinal.

  • Method

    Parte LOINC que identifica el método cuando forma parte del significado del término.

  • Fully-Specified Name LOINC

    Nombre construido a partir de las partes definitorias de un término LOINC.

  • Estado LOINC

    Estado editorial como active, discouraged o deprecated que debe revisarse al mapear.

  • ICD-11 Foundation

    Componente multidimensional de la ICD-11 del que se derivan linearizaciones.

  • Linearización

    Subconjunto estructurado de la Foundation diseñado para un uso particular.

  • ICD-11 MMS

    Linearización de ICD-11 para estadísticas de mortalidad y morbilidad.

  • Extension code

    Código ICD-11 utilizado para añadir detalle dentro de las reglas de postcoordinación aplicables.

  • Mapeo terminológico

    Relación documentada entre una expresión o código de origen y uno o más destinos.

  • Código local

    Identificador creado por un sistema u organización antes de su normalización terminológica.

  • Equivalencia exacta

    Relación en la que origen y destino representan el mismo significado para el propósito definido.

  • Origen más amplio

    Relación en la que el concepto de origen abarca más significado que el destino.

  • Origen más estrecho

    Relación en la que el concepto de origen es más específico que el destino.

  • Equivalencia parcial

    Relación de solapamiento sin identidad semántica completa.

  • Sin correspondencia

    Resultado en el que no se identifica destino suficientemente equivalente.

  • Mapa direccional

    Mapa cuya validez está definida de origen a destino y no implica inversibilidad.

  • Pérdida semántica

    Información del significado de origen que no queda representada en el destino.

  • Cobertura de mapeo

    Proporción de elementos de origen con alguna correspondencia, que no mide por sí sola exactitud.

  • Control positivo de mapeo

    Caso con correspondencia conocida usado para comprobar que el método puede recuperarla.

  • Control negativo de mapeo

    Caso incompatible usado para comprobar que el método puede rechazar una asignación incorrecta.

  • Caso ambiguo

    Caso en el que la información disponible no permite sostener una correspondencia única.

  • Revisión terminológica

    Evaluación independiente de una selección o mapa utilizando evidencia y reglas explícitas.

  • Inactivación

    Cambio de estado que indica que un componente ya no debe usarse como contenido activo según la terminología.

  • Asociación histórica

    Relación que ayuda a gestionar componentes inactivos y posibles sustituciones o equivalencias históricas.

  • Sistema terminológico

    Identificador del vocabulario o clasificación al que pertenece un código.

  • Trazabilidad terminológica

    Capacidad de reconstruir código, sistema, versión, fuente, criterio, autor y cambios de una decisión.

  • Semántica clínica

    Significado clínico que debe preservarse más allá de la forma textual o técnica.

  • Binding terminológico

    Restricción que conecta un elemento de un modelo de información con un value set; se formaliza en U4.

  • Interoperabilidad semántica

    Capacidad de intercambiar información preservando significado suficientemente compartido para el uso definido.

Cierre de la unidad

Seleccionar, representar y auditar terminologías clínicas según el significado que se desea registrar: usar SNOMED CT para conceptos clínicos con relaciones formales, LOINC para identificar observaciones y pruebas por sus atributos, e ICD-11 para clasificación estadística, conservando sistema, versión, código, texto y contexto. La unidad enseña mapeo y equivalencia con incertidumbre explícita, reutiliza el modelo de información de U2 y reserva para U4 el transporte mediante HL7/FHIR. Conecta especialmente con Historia clínica electrónica: La HCE necesita distinguir texto local, concepto normalizado, sistema y versión para que los registros longitudinales de U1 conserven significado, Laboratorio clínico: LOINC permite normalizar qué observación o prueba se identifica; la muestra, propiedad, tiempo y método pueden cambiar el código apropiado, Sistemas de ayuda a la decisión: Value sets y conceptos clínicos correctamente versionados reducen ambigüedad en reglas, aunque la utilidad clínica de una regla exige validación adicional, Epidemiología y estadísticas sanitarias: ICD-11 MMS permite clasificación para morbilidad y mortalidad, con granularidad y reglas distintas de la terminología clínica detallada. Material educativo en estado review basado exclusivamente en escenarios y registros sintéticos. No constituye codificación clínica profesional, codificación de mortalidad o facturación, asesoría terminológica institucional, diagnóstico, prescripción ni implementación productiva. No se deben introducir datos identificables de pacientes. Los códigos y ejemplos deben verificarse contra la edición y licencia aplicables antes de cualquier uso real. U3 enseña significado y mapeo; U4 cubre interoperabilidad FHIR/HL7 y bindings, U5 gobernanza y U6 conformidad/implementación.
